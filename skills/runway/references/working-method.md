# Как вести работу

> **В составе runway.** Этот файл про механику: PR, проверки, слияние, делегирование. Порядок работ,
> границы автономии и память между сессиями задают `SKILL.md`, `loop.md` и `PROFILE.md`.

Аудит части продукта — это десятки правок за одну сессию. Без дисциплины он превращается в
кашу из коммитов, в которой ни владелец, ни ты сам через неделю не разберётесь.

## Разведка перед первым проходом

```
1. Размер и границы: сколько файлов, сколько строк, где начинается чужое.
2. Карта: экраны/маршруты, клиенты API, общие слои, серверные обработчики этой части.
3. Базовая линия: прогнать ВЕСЬ набор тестов до первой правки.
4. Инструменты проекта: как запускаются тесты, типы, линт, генерация контрактов и строк.
```

Базовая линия важнее, чем кажется: без неё первое же падение тратит час на вопрос «это я или
оно было?». Если что-то уже красное — это первая находка, и чинить её надо до аудита.

Узнай **правила проекта** до того, как писать код: язык комментариев, стиль коммитов,
привычный размер PR, требования к атрибуции, запреты (например, никаких приписок про ИИ),
сторожевые тесты каталога строк. Нарушенное правило проекта обесценивает хорошую находку.

## Делегирование инвентаризации

Механический обход экранов отдавай параллельным агентам — это самая окупаемая часть
делегирования. Три задания, которые работают почти всегда:

**A. Двойные нажатия.**
> Просмотри все компоненты `<путь>`, кроме тестов. Для каждой кнопки/формы, вызывающей
> изменяющий запрос, определи: есть ли состояние занятости и выставлен ли `disabled` на время
> запроса. Верни две таблицы — защищённые и незащищённые (файл:строка, что за действие, чем
> опасен повтор). Ничего не меняй.

**B. Состояния разделов.**
> Для каждого экрана/секции, который грузит данные: есть ли индикатор ожидания, ошибка, кнопка
> повтора, пустое состояние; проходит ли текст ошибки через общий разбор ошибок или показывается
> общей фразой/сырым текстом. Верни таблицу и отдельным списком — тупики. Ничего не меняй.

**C. Текст и форматы мимо общей инфраструктуры.**
> Найди строки интерфейса мимо каталога, свои форматтеры дат/чисел/денег рядом с общими, ручную
> плюрализацию, английские слова в интерфейсе. Комментарии и имена переменных не считаются.
> Верни таблицу, отсортированную по заметности для человека. Ничего не меняй.

Правила делегирования:

- Агенту — **чтение и отчёт**, себе — решения. Исключение: крупная механическая переработка по
  готовому образцу (перевести десять разделов на общий хук) — её можно отдать, но с точным
  образцом, требованием прогнать проверки и запретом трогать чужие файлы.
- Скажи агенту, какие файлы **твои**, если работаешь параллельно: две правки одного файла из
  разных мест дают испорченный файл и потерянное время.
- Результат агента проверяй сам: прогон тестов и просмотр диффа выборочно. Отчёт «всё зелено»
  без твоего прогона — не доказательство.
- Агент, честно сказавший «это красное было до меня» — норма; не принимай молча, проверь.

## Один класс — один PR

Заголовок PR — **мысль**, а не категория:

- плохо: `fix: add timeouts`, `refactor loading hooks`;
- хорошо: «Запрос с пределом ожидания и повтор без дубля», «Раздел, который не загрузился,
  называет причину», «Молчаливых отказов больше нет».

Тело PR отвечает на три вопроса:

1. **Чем это было для человека** — конкретно, без жаргона.
2. **Что сделано** — списком, с указанием корня, а не файлов.
3. **Что проверено** — числа: тесты, типы, линт, CI.

Отдельным абзацем — **что изменилось в поведении**, если изменилось (например: «в разделе ролей
после сохранения теперь на миг показывается скелетон вместо старого списка»). Владелец не
должен узнавать об этом из эксплуатации.

Размер PR: один класс целиком. Если класс огромный (двадцать разделов), допустимо разбить по
слоям (механизм → применение), но не оставлять его полузакрытым между сессиями.

## Сторожевые тесты

Тест аудита отличается от обычного: он **объясняет причину**.

```
// Ответ потерялся по дороге — человек нажимает «Отметить оплаченным» второй раз. Если бы ключ
// попытки был новым, платёж отметился бы дважды: первый запрос до сервера дошёл.
it('повтор после неудачи несёт тот же ключ попытки', ...)
```

Такой тест переживает рефакторинг и не даёт классу вернуться. Если правишь существующий тест —
остановись и спроси себя: поведение изменилось намеренно или я подгоняю тест под свой код?
Подробнее — [honesty.md](honesty.md).

Отдельно: если проект имеет сторожевые тесты каталога строк (мёртвые ключи, паритет языков,
глоссарий) — они твои союзники. Мёртвый ключ удаляется **в том же PR**, где исчезла причина его
существования, иначе следующая ветка ловит чужой красный тест.

## Проверки перед «готово»

Минимум, который прогоняется перед каждым коммитом:

```
тесты пакета/приложения        — полностью, не выборочно
компилятор/типы                — чисто
линтер                         — чисто
сторожевые тесты каталога      — если проект их имеет
тесты сервера                  — если правка затрагивает сервер
генерация контрактов/строк     — перегенерировать и убедиться, что нет диффа
```

**Флак — твоя зона.** Если прогон изредка краснеет, не списывай на «бывает»: выясни причину.
Частая — тест проверяет момент времени («статус сейчас такой»), а не свойство («ожидание больше
не показывается»). Перепиши на свойство — станет и надёжнее, и понятнее.

## Слияние

Аудит порождает цепочку PR. Два рабочих варианта:

**Независимые ветки от основной** — предпочтительно. Каждый класс живёт отдельно, мержится
отдельно, конфликты решаются один раз. Возможно, когда классы трогают разные файлы.

**Стек (каждый PR на предыдущем)** — когда классы трогают одни и те же файлы. Дисциплина стека:

- мержить **снизу вверх** и **сразу**, не копить восемь ветвей;
- после слияния родителя проверять, что дочерний PR перенацелен на основную ветку
  (`--base main`), иначе он вольётся в уже слитого родителя и в основную ветку не попадёт;
- **не удалять ветку при слиянии** (`--delete-branch`), пока у неё есть дочерние PR: удаление
  ветки закрывает их;
- если стек всё-таки «схлопнулся внутрь себя» — не пересобирать историю: последняя ветка стека
  содержит всё, из неё делается один сборный PR в основную ветку. Это нормальный запасной ход,
  и он безопаснее, чем правка истории.

Перед удалением веток в конце: проверить, что содержимое действительно в основной ветке
(`git log main..branch` — только merge-коммиты), и что удаление никого не ломает. Удаление
необратимо — если владелец не просил, **спроси**.

## Сдача

1. **Документация.** Раздел в журнале прогресса: что нашлось в каждом проходе (короткими
   абзацами «было → цена → стало»), что закрыто, и **отдельным блоком** — что не сделано
   осознанно, с причиной и ценой. Обновить список следующих работ: закрытая часть уходит,
   всплывшие вопросы владельца добавляются.
2. **Память проекта.** Короткая запись: часть, даты, номера PR, классы находок одной строкой,
   осознанные «не делаем», ссылки на соседние разборы. Она нужна следующей сессии, а не отчёту.
3. **Отчёт человеку** — по форме из SKILL.md: человеческим языком, с ценой находок, с честным
   «вот это я не тронул и почему», и с предложением следующего значимого куска по проекту.

## Оценка объёма

Ориентиры из практики, чтобы не обещать лишнего:

- часть в 5–20 тысяч строк — три прохода за одну длинную сессию, 8–12 PR;
- первый проход даёт 6–10 классов, второй — 4–8 находок, третий — 8–15;
- на каждый класс закладывай цикл «найти → починить корень → тест → прогон → PR»;
- время съедают не правки, а **проверки и слияние** — планируй их, а не надейся.
