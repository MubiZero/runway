# Выбор и смена технологий

Новое не значит лучше. Менять технологию хочется чаще, чем нужно, а цена миграции платится
всегда. Правило: **менять только при измеримом выигрыше под ограничения этого проекта**, и
делать это так, чтобы можно было вернуться.

## Когда не менять

- Текущее работает, выигрыш на глаз и «так модно».
- Миграция съест больше времени, чем остаётся до пилота.
- Новая технология не поддерживает целевую среду (см. пример ниже).
- Команда или ты знаешь новое хуже, а ошибки в нём стоят дорого.
- Владелец в интервью выбрал «чинить, не менять».

## Процедура

1. **Выпиши ограничения.** Целевые ОС и их версии, железо (RAM, диск, CPU), сеть, размер
   дистрибутива, как ПО попадает на машины, сколько их, кто поддерживает. Из `PROFILE.md`.
2. **Проверь факты, а не память.** Версии и совместимость берёшь из официальной документации
   и заметок о релизах (инструмент документации, если есть, или веб), затем из changelog,
   потом уже из статей. Знания модели о версиях устаревают: проверь актуальную версию,
   поддерживаемые ОС и дату окончания поддержки.
3. **Сравни 2–3 кандидата** по таблице:
   | Критерий | Текущее | Кандидат A | Кандидат B |
   |---|---|---|---|
   | Поддержка целевых ОС и версий | | | |
   | Размер дистрибутива, RAM на старте | | | |
   | Поведение при плохой сети / офлайн | | | |
   | Зрелость: частота релизов, мейнтейнеры, срок жизни | | | |
   | Экосистема и объём живого кода и ответов | | | |
   | Стоимость миграции (модули, дни) | | | |
   | Лицензия и безопасность (известные дыры) | | | |
4. **Замерь, если можно.** Маленький прототип или бенчмарк на целевой среде дороже слов.
   Цифры «RAM на старте», «размер установщика», «время холодного старта» это
   аргументы, остальное мнения.
5. **Миграция поэтапно:** через адаптер или флаг, старый путь живёт до паритета, у каждого
   этапа проверка и откат. Нигде не должно быть состояния «наполовину».
6. **Запиши решение** в `docs/release/decisions/NNNN-название.md` (шаблон ниже), даже если
   решил **не менять**: следующая сессия не начнёт тот же спор заново.
7. **Крупную миграцию** (затрагивает много модулей, меняет рантайм или базу) ставь после
   P0/P1, делай на отдельной ветке, а в профиле должен стоять разрешающий режим.

## Что значит «лучше» для разных проектов

Не бери критерии из головы, бери из ограничений:

- слабые ПК и старая ОС: размер, RAM, совместимость с рантаймом важнее новизны;
- плохая сеть: дельта-обновления, локальный кэш, повторы и офлайн-режим, протокол с
  хорошей устойчивостью к потерям (например, HTTP/3 между клиентом и облаком там, где его
  поддерживает вся цепочка, а не только сервер);
- много однотипных машин: раздача обновлений внутри локальной сети вместо N загрузок
  из интернета, автообновление без ручных кликов;
- маленькая команда: зрелая экосистема и объём живого кода, на котором ИИ и люди уже
  набили руку, важнее экзотики.

## Пример: когда «самое новое» не подходит

Требование «работает на Windows 7» и желание перейти на современный десктопный фреймворк.
Фреймворки на основе системного веб-компонента (на Windows это WebView2) зависят от того,
поддерживает ли Microsoft этот компонент на целевой ОС: на Windows 7 и 8 его поддержка
прекращена. Electron прекратил поддержку Windows 7 с определённой версии. Значит выбор
«лёгкий новый фреймворк» может оказаться несовместимым с частью парка. **Проверь актуальные
сведения по документации**, не по этому примеру, и задай владельцу вопрос: «сколько машин
реально на Win7, можно ли держать для них старую ветку клиента?» Тогда решение осознанное.
